# 引元系统模型

## 职责与知识状态

本文件拥有引元跨场景的概念对象、运行循环、决策维度、任务与能力调度、闭环及横向约束。产品定位与盒子角色引用 [引元](../products/origin.md)。

这是产品层系统设计基线，不是数据库表、部署方案或已实现接口清单。来源中的建议模型经本轮整理；具体字段、阈值、算法、性能与协议需后续设计验证。垂类可扩展业务能力，但继续遵循统一对象关系、权限和结果验证机制。

## 1. 概念对象与关系

| 对象 | 含义与关系 |
| --- | --- |
| Space 空间 | 物理环境及区域，承载人、设备、状态与事件 |
| Person 人 | 服务对象或参与者，通过角色及组织关系确定责任与授权 |
| Device 设备 | 位于空间、具有状态、提供一种或多种能力的物理资源 |
| Capability 能力 | 可以被匹配、组合、调用的功能；由设备或服务资源提供 |
| State 状态 | 对对象当前情况的记录与解释，带有证据和时间语境 |
| Event 事件 | 值得关注的变化或触发，不等于应执行的任务 |
| Task 任务 | 围绕目标的一次执行实例，关联约束、能力、计划与完成条件 |
| Service 服务 | 面向目标提供的可复用服务，可通过任务调用并由多种能力实现 |
| Policy 策略与约束 | 限定判断、资源调用、动作和责任边界 |
| Memory 记忆 | 用于后续理解的历史、规律及经验，与实时状态区分 |

辅助概念：Scene 场景组织具体业务目标与流程，不等同于 Space；Resource 资源包含设备和可调用外部服务；Role/Organization 描述参与和组织关系；Goal、Action、Result 分别描述目标、动作和结果。它们是概念关系，是否独立建模由后续方案确定。

核心关系：人/设备位于空间；资源提供能力；事件关联人、空间、设备或任务；任务需要能力；策略约束判断与行动；动作产生结果并更新状态与记忆。

## 2. 状态、事件与情境

空间理解分为原始状态、语义状态和情境三层：

- 原始状态：设备或资源提供的数据。
- 语义状态：对数据含义的解释。
- 情境 Situation：结合关系、历史、策略、任务和上下文形成当前情况的理解。

保持数据来源、采集时间、有效性以及观测/推断/已确认的区别；推断保留置信度和可纠正性。未知、过期或失联不自动解释为正常。

事件可来自指令、计划、状态变化，也可被标记为异常或综合推断。前者描述触发来源，后者描述评价或证据形成方式，允许同时存在，不强制采用五选一分类。

事件进入情境理解和决策后，才决定是否形成任务。识别异常不等于自动执行。

## 3. 两个持续循环

- **认知循环**：感知 → 状态更新 → 事件识别 → 情境理解 → 认知更新 → 继续感知。
- **服务循环**：情境 → 介入判断与目标 → 任务规划 → 能力调度与执行 → 验证 → 反馈。

总体逻辑为“感知 → 理解 → 判断 → 规划 → 调度 → 执行 → 验证 → 学习”。这是依赖与反馈关系，不是阻塞式单一流水线；认知持续进行，服务可并发、暂停、调整和结束，结果回到状态与记忆。

## 4. 功能分层与逻辑引擎

| 功能层 | 内容 | 主要对应职责 |
| --- | --- | --- |
| 交互与管理层 | 呈现、提醒、确认、设置与解释 | 跨引擎交互入口 |
| 服务编排与执行层 | 规划、能力匹配、资源选择、执行、异常处理和验证 | Action Engine |
| 智能决策层 | 情境评估、介入必要性、目标与策略选择 | Decision Engine |
| 空间状态与记忆层 | 对象、关系、状态、历史、规律与事件情境 | Space Engine、Event Engine |
| 设备与能力接入层 | 发现、协议适配、注册、同步、指令与服务接口 | 提供统一接入支持 |
| 资源层 | 感知、交互、健康、智能、服务设备及外部服务 | 提供实际能力 |

四个逻辑引擎分工：Space 维护对象、关系、状态与记忆；Event 识别事件和情境；Decision 决定介入、目标与策略；Action 负责执行计划、能力组合、调度及结果验证。Decision 确定目标与策略，Action 将其细化为可执行计划，必要时返回重新决策。

六层描述功能位置，四引擎描述逻辑职责，双循环描述运行方式；三者不是三套系统，也不预设必须拆成四个进程或服务。智能决策属于引元系统职责，具体模型或其他产品的调用关系另行确认。

## 5. 主动服务决策：三个独立维度

先判断是否需要介入、何时介入、目标是什么、采用什么方式、允许做到什么程度。综合风险、紧迫性、判断置信度、服务价值、打扰成本和权限。

| 维度 | 定义 | 使用约束 |
| --- | --- | --- |
| 介入方式与权限 | 观察记录、提醒、建议、确认后执行、自主执行；每个实际动作仍需核对授权 | 方式不是权限递增通行证，提醒和信息披露也有授权边界 |
| 紧急程度 | 决定响应时限、任务优先级和何时进入预定义紧急流程 | 紧急不自动扩大动作权限；阈值和时限由场景定义 |
| 参与与协同对象 | 确定谁接收信息、谁确认、谁执行、谁接手以及无响应后的路径 | 对象可组合，不以人员身份直接推断权限或紧急程度 |

不再把来源 L0–L5 作为统一等级表；其中观察到自主执行纳入第一维，“紧急/强制流程”纳入第二维并继续服从权限与协同约束。康养原 0–4 级也不与其逐级对应，领域应用见 [康养产品](../products/origin-home-eldercare.md)。

每项决策应能说明证据、目标、三个维度的选择及下一步条件。多目标或资源冲突时，依据场景策略与授权仲裁；不能确定时使用确认、等待、替代或降级，不静默执行冲突动作。

## 6. 任务、能力与资源调度

任务以目标为中心，至少描述 Goal、Constraints、Priority、Deadline、Required Capabilities、Success Criteria。具体执行计划可以绑定已选择的设备，通用任务目标不固化设备型号。

任务目标 → 子任务 → 所需能力 → 候选资源 → 执行计划 → 执行 → 结果验证。

能力描述应能回答输入输出、前置条件、适用空间、权限、当前可用性及如何确认效果。匹配资源时综合空间、在线状态、匹配度、用户/组织偏好、优先级、成本与可用性，允许能力组合和资源替代。

设备可以同时提供感知、交互和执行能力。检测某个指标不等于能够改变该指标；能力与效果必须有各自证据。

任务设计需覆盖待确认、执行、取消、超时、失败、部分完成及恢复等情况；具体状态枚举后续定义。多人任务和设备占用也需有冲突处理，避免重复动作或遗漏服务。

## 7. 结果验证与学习

闭环为 Goal → Action → Result，至少区分：

1. 指令已发送或被接收。
2. 动作实际执行，有对应状态或回执。
3. 目标是否达成，有匹配成功条件的证据。

前一步完成不证明后一步成功。结果应能表达完成、部分完成、未知或失败，并确定是否调整、继续、转交或结束任务。反馈用于更新空间状态、服务依据与记忆。

学习可在已授权范围内改善时机、方式、资源选择和低风险策略；不能自行扩大权限或改写高风险规则。业务计划、目标和责任配置的变更由相应垂类明确授权机制。规律与推断保留来源、纠正和撤回能力，不将一次结果自动推广为长期规律。

## 8. 横向约束与垂类落地

- **权限与主动性**：明确谁可感知、使用或披露哪些信息，调用哪些资源，哪些动作需确认；支持授权撤回和人工停止。具体数据保留、删除与责任规则在落地方案中确定。
- **安全与可靠性**：明确设备失联、判断错误、任务失败、冲突指令和异常退出的影响；按可用能力替代或降级，恢复前核对任务与资源状态，避免重复执行。不预设所有服务可离线运行。
- **可解释与可追溯**：记录判断来源、介入原因、策略、资源调用、结果证据及人工接手状态。

每个垂类及具体场景应交代服务对象与目标、空间与角色、资源及专属能力、业务流程、事件条件、决策三维、完成标准、最低运行条件与失败恢复路径。领域阈值、医疗判断、设备效果和通知回执不能从通用模型推断。
