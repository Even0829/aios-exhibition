# AIOS 家庭康养陈展：事实与边界

本文件拥有本次陈展的目标、受众、现场输入、范围及事实来源；作为陈展工作的业务入口。体验结构归 `../../architecture/aios-exhibition-experience.md`，设计与还原规范归 `../../specs/aios-exhibition-design-system.md`，完整路由见 `../../README.md`。

本次陈展是[引元家庭康养产品](origin-home-eldercare.md)能力与具体场景的样板表达；其知识底座来自[引元](origin.md)。本文件只拥有样板范围，不重新定义底座或垂类产品。以下“已确认”表示用户确认的设计依据，不自动表示已由本项目完成技术验证或实现。

## 1. 陈展目标与受众

依据：来源 A、B、O。

- 为引元家庭康养产品设计适合陈展现场的完整 Demo，以普通游客为主要体验者，以电视为核心交互和产品表达载体。
- 本次陈展中的 INT AIOS 指向[引元](origin.md)，名称及定义以该 Owner 和术语表为准。
- 家庭康养是引元的垂类落地，也是本次陈展选取的能力展示切入口。重点是系统统一接入设备、理解人和空间、综合分析、作出决策并主动组织康养服务。
- 多数游客应能在没有讲解员帮助时独立完成；体验简单、清晰、直观，时间不宜过长，暂不限定具体分钟数。
- 产品的长期服务对象仍以老人及家庭为主；不能据此把现场游客默认设计为老人，也不能把电视在陈展中的核心地位推广为产品运行前提。
- 现场有可用拾音和播报设备；考虑环境复杂，语音作为辅助，减少不必要语音交互。

## 2. 与已有产品文档的关系

依据：来源 A、C、O。

- 后续康养产品与具体场景继续依靠引元设计和验证；陈展中的设备选择、模拟数据、页面和交互不限定长期产品能力，样板可运行也不等于真实产品能力已验证。
- 本项目重新设计陈展故事；旧陈展 Demo 代码、素材、页面、故事框架和 UI/UX 规格已从当前仓库清理，不作为此次设计基线。
- “五大核心场景能力”、相关业务场景、共用机制和设备组合文档保留，用于长期产品知识；不作为本次陈展的故事模板、逐项覆盖清单或默认阅读前置。
- 旧业务文档中的设备组合不等于本次陈展设备范围。陈展范围以本文件为准；涉及扩展产品定义时再按产品导航补充读取。
- 不继承旧 Demo 的固定页面数、状态数、组件选型、配色、尺寸、时序或交互规则。

## 3. 用户提供的设备与能力输入

依据：来源 A、B。该表是本轮设计输入，不是接口联调或硬件验收清单。

| 设备或能力 | 用户描述的输入／输出 | 证据程度与边界 |
| --- | --- | --- |
| 视频摄像头及分析模型 | 获取体验位置上的人物视频，估计男女与年龄老少等基础外观信息 | 用户描述；具体模型、输出字段、准确度和接口未核验；外观估计不等于身份确认或医疗判断 |
| 射频设备 | 判断服务范围是否有人，判断跌倒事件 | 用户描述；范围、事件格式与判定能力未核验，展示异常时使用疑似状态或明确模拟 |
| 空气消杀机 | 感知空气颗粒物谱、PM2.5、CO₂、VOC、温度、湿度；支持送风净化 | 用户描述；各项检测与控制能力待接入核验，不能推断机器能调节所有被检测指标 |
| 睡眠带 | 检测心率、呼吸、上床／离床；放在座位下用于就位判断和坐姿采集 | 用户确认坐姿方案已实测可行；约 30 秒获得稳定数据为用户估计，尚非验证时限 |
| 医疗 AI 模型 | 基础医疗问询与建议 | 用户描述；调用方式、具体服务范围和接口未核验，不作为医疗诊断能力 |
| 电视及现场音频设备 | 电视表达与交互，辅助拾音和播报 | 用户确认现场音频设备可用；电视功能仅表达待接入，不做真实操作或节目切换；Demo 的具体输入方式留待交互设计 |

这批设备不是封闭清单。后续可能加入其他设备，增强 AIOS 感知、分析与服务能力；设计应支持扩展，不能将当前设备数量和名称固化为系统能力边界。

## 4. 本阶段交付边界

依据：来源 D、E、F、H、J、K、L、P、Q、R。

- 用户已制作正常路径的完整 Figma 设计稿及一套基础 Figma UI 组件；2026-09-04 已建立静默待机首页及本页基础前端组件；当前落地范围见设计规范第 8 节。
- 先逐页还原并连通正常路径 Demo，再判断是否满足陈展场景和核心产品价值，随后补充完善。
- 首轮使用 Mock 数据、模型结果与设备反馈，真实设备和模型接入放到后续阶段；本阶段可运行不代表真实联调已完成。
- 已允许加入明确标记的空气异常、身体不适、疑似跌倒模拟情境。头像浮窗作为三个异常故事的查验入口，默认自动体验仍保持正常路径。空气异常现使用 CO₂ 持续偏高的连续 Mock，调度空气消杀机执行低扰动空气优化并以运行回执和后续读数形成闭环；暂不加入开窗／通风提醒。黄色语义由事件状态传入，整套流程不作为真实阈值、设备联调或空气消杀机降低 CO₂ 的能力结论。
- 开始、选择、跳过、退出等具体操作方式留到实际交互设计，不是本轮文档或故事梳理的前置条件。
- 2026-09-10 用户确认身体不适分流故事并授权还原：睡眠带心率偏快后结合本人回答分流；2026-09-18 追加“持续未获得本人回应”的 15 分钟关注 Mock，后续数据恢复平稳则反馈记录，数据仍未恢复或进一步异常则升级为红色持续守护和预设紧急联系人同步中表达。前端仍只做点选问答、压缩计时与陪护／协同 Mock，不接入医疗模型、麦克风、真实 15 分钟定时复查、联系人通知或外部回执。普通不适、持续无回应与明显不适的语义来自回答／确认状态及事件配置，不由心率数值单独决定；具体流程见[人体不适故事](../../architecture/exhibition-stories/body-discomfort.md)。
- 2026-09-11 用户确认疑似跌倒首版 Demo：射频设备是唯一模拟事件来源，必须在已感知到人在空间后才可触发，但可抢占任意正在运行的体验流程。确认组件提供“我没事／我需要帮助／无人回应”三个演示选项；求助或无人回应后发起现场协同，红色持续守护等待“现场人员”接手，再升级通知“预设紧急联系人”。首版不模拟对方确认或现场接手回执，不展示姓名、电话、App、短信或 120，不自动进入成功反馈或记忆结论。
- 电视操作与节目切换不做真实接入，Demo 仅反馈“待接入”；不要求实现模拟电视节目。
- 设备功能按正常家庭需求设计，计划由 Home Assistant 统一承接小米、涂鸦等设备与服务能力，但界面不向家庭用户暴露 Home Assistant。电视负责设备浏览、状态展示和语音控制；手机端首期按小程序设计，负责账号与设备添加、配置、完整手动控制及家庭外远程控制。最小产品服务端的首期必要性和产品职责已确认；其技术架构、真实 Home Assistant 适配、小程序远程通道和品牌授权仍未完成选型或接入验证。
- 电视端当前只保留“家庭设备／接入账号”。设备和账号列表分别提供“添加设备／添加账号”，在原右侧内容区展示手机二维码接续并可返回；账号卡提供“账号管理”并进入对应账号的手机接续，不跳转关联设备筛选，也不设置电视账号详情页或独立“在手机上管理”栏目。原四台在线设备在本轮展示中均归涂鸦；其余品牌归属、普通家庭设备、状态与控制是可替换的 Mock 样本。
- 电视设备列表按空间筛选并优先展示在线设备，不增加状态筛选；设备详情在语音之外保留基础遥控兜底，可展示并调节设备开关、亮度、色温等明确能力，账号与完整设备配置仍由手机小程序承接。
- 手机小程序首期只服务设备中心，使用家庭管理员／家庭成员两级角色，覆盖设备、AI 助手、消息和我的四个入口；与电视共用同一家庭、账号、设备和状态样本。真实家庭首期确认建设可扩展的最小产品服务端，承接身份、家庭权限、品牌接入编排、远程控制、消息、AI 和跨端同步，但不重复建设 Home Assistant 的品牌适配和控制引擎；完整规则见[设备中心 PRD](../../specs/device-center-prd.md)。
- 场景按体验区内一位体验者推进，不扩展复杂多人识别与关联；具体来访、就位与服务衔接由体验架构定义。
